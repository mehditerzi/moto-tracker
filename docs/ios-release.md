# iOS releases — how a push becomes a build in App Store Connect

Pushing to `main` builds the iOS app in Xcode Cloud and delivers it to App Store
Connect. This describes what runs, what you still have to do by hand, and the
three failure modes that look like something else.

---

## What is automated, and what is not

| Step | Who |
|---|---|
| Build the web app, `cap sync`, archive, sign | Xcode Cloud, on every push to `main` |
| Stamp a unique build number | Xcode Cloud (`ci_pre_xcodebuild.sh`) |
| Deliver the build to App Store Connect / TestFlight | Xcode Cloud |
| Bump the **version** users see (1.2 → 1.3) | **You**, in the Xcode project |
| Submit for review | `scripts/asc-submit-version.mjs` (or you, in App Store Connect) |
| Release to users after approval | **You** (or App Store Connect's auto-release) |

**Apple review cannot be automated.** "Auto" here means a push produces a
signed build sitting in App Store Connect, ready to submit — not a new version
in front of users. Anyone who tells you otherwise is describing TestFlight.

---

## The Xcode Cloud workflow

One workflow, **`Default`**, on the `Garajım` product:

- **Trigger** — any push to `main`
- **Container** — `apps/web/ios/App/App.xcodeproj`, scheme `Garajım`
- **Action** — `ARCHIVE`, `buildDistributionAudience: APP_STORE_ELIGIBLE`
- **Post-actions** — none, and none are needed to submit.

### `APP_STORE_ELIGIBLE` really does deliver — no post-action required

An earlier version of this document claimed delivery needed a TestFlight
post-action added by hand. **That was wrong**, and it is worth recording why so
nobody re-adds a step that does nothing.

Measured on 2026-08-30: the `Default` workflow has `postActions: undefined`,
and builds **9 and 10** both arrived in App Store Connect as version `1.3`,
`processingState: VALID`. An `ARCHIVE` action with
`buildDistributionAudience: APP_STORE_ELIGIBLE` archives, signs, **and
uploads**. That is all a submission needs.

A post-action is only for pushing a delivered build onward to **TestFlight
tester groups**. If you never use TestFlight, you never need one — which is
lucky, because the API does refuse to write it:

```
409 — 'postActions' is not an attribute on the resource 'ciWorkflows'
```

If you *do* want internal testers, add it once by hand:
**App Store Connect → Xcode Cloud → Manage Workflows → `Default` →
Post-Actions → + → TestFlight (Internal Testing) → Save.**

The real diagnostic for "my build never showed up" is not the post-action.
Check, in this order: the build run actually **succeeded** (runs 6–8 failed on
Node 22 and produced nothing), and the build is not still in
`PROCESSING`. Query it directly rather than watching the UI:

```
GET /v1/builds?filter[app]=6783515081&sort=-uploadedDate&include=preReleaseVersion
```

A second workflow, **`Garajim`**, is **disabled on purpose**. It only ran
`BUILD` (compile, no archive, no upload) on the same trigger, so every commit
paid for a second build that produced nothing. Leave it disabled or delete it;
do not re-enable it.

Inspect the live configuration any time:

```
ASC_ISSUER_ID=<uuid> node -e '…'   # see scripts/asc-list-iap.mjs for the JWT pattern
```

## `ci_scripts/` — why the build needs them

`apps/web/ios/App/ci_scripts/` runs inside Xcode Cloud, beside the `.xcodeproj`.

### `ci_post_clone.sh` — builds the web app

This is **required, not an optimisation.** Two things the iOS target needs are
generated by `cap sync` and deliberately not committed:

- `App/App/public/` — the built web app (gitignored via `dist`)
- `App/App/capacitor.config.json` — `server.url`, `allowNavigation`,
  `packageClassList`

A fresh clone has neither. Without this script the archive ships with **no
`packageClassList`**, so BackgroundGeolocation, Haptics and PushNotifications
never register; and **no `server.url`**, so the WebView never loads the live
site. `xcodebuild` still succeeds. You get a signed, uploadable, broken app.

That is the same failure that made in-app purchase impossible for two months —
a plugin present in the source and absent from the binary — so the script
asserts on both artefacts and fails the build rather than shipping one.

It runs `pnpm --filter @mototracker/web cap:build`, the same command used for a
local device build, so CI cannot drift from what you run by hand.

### `ci_pre_xcodebuild.sh` — stamps the build number

`CURRENT_PROJECT_VERSION` is hard-coded to `1` in the project. App Store Connect
rejects an upload whose `CFBundleVersion` it has already seen for that
`CFBundleShortVersionString`, so the first automated upload would succeed and
every one after it would fail with *"The bundle version must be higher than the
previously uploaded version"* — which reads like a signing problem and is not.

`CI_BUILD_NUMBER` is monotonic per workflow, so the script writes it with
`agvtool`. **`MARKETING_VERSION` is left alone**, under human control.

## Shipping a new version

1. **Bump `MARKETING_VERSION`** in `apps/web/ios/App/App.xcodeproj` (e.g. 1.2 →
   1.3). Only needed for a user-visible version; TestFlight builds of the same
   version just need a new build number, which is automatic.
2. **Push to `main`.** Xcode Cloud builds and delivers.
3. **The build appears in App Store Connect** under the app's *Builds* within
   roughly 15–30 minutes, first as `PROCESSING`, then `VALID`.
4. **Create the version, attach the build, then submit:**

   ```
   ASC_ISSUER_ID=<uuid> node scripts/asc-submit-version.mjs           # dry run
   ASC_ISSUER_ID=<uuid> node scripts/asc-submit-version.mjs --apply   # submit
   ```

   The submit **is** scriptable — an earlier version of this document said it
   was the one step that was not, and see the failure mode below for what that
   cost. The script preflights the things that block a submission quietly,
   including `usesNonExemptEncryption`, which blocks while it is `null` and is
   easy to miss because the UI only raises it at the last step.
5. Choose manual or automatic release on approval.

### Web-only changes do not need any of this

The app loads the live site through `server.url`, so a change to `apps/web`
reaches users **on next app launch** as soon as you deploy the server — no
build, no review. Only native changes (Swift, `Info.plist`, `capacitor.config`,
plugins, entitlements) need a new binary.

## Three failure modes that look like something else

**"The app is broken" when nothing is broken — the version was never
submitted.** This is the expensive one, because every dashboard looks healthy
while it happens. On 2026-09-05 the reported symptoms were a black screen and
Sign in with Apple failing. Both were real, both had been fixed on 2026-08-28,
and both fixes were sitting in App Store Connect: version 1.3,
`PREPARE_FOR_SUBMISSION` since 2026-08-30, build 10 attached and `VALID`,
metadata and screenshots complete, ten subscriptions `APPROVED`. Users were on
**1.1 from 2026-07-20** — which shipped with `server.url` but no
`allowNavigation`, so Apple's sign-in page opened in Safari and set the session
cookie in Safari's jar, and the user returned to the app still signed out.

Nothing was stuck and nothing was rejected. Nobody had pressed submit.

The tell: `appStoreState` is `PREPARE_FOR_SUBMISSION` on a version whose build
is `VALID`, and `/v1/reviewSubmissions` has nothing newer than the previous
release. Check it in one command, and note that a green Xcode Cloud run means
only that a binary exists — it says nothing about whether anyone shipped it:

```
ASC_ISSUER_ID=<uuid> node scripts/asc-submit-version.mjs   # dry run; reports state
```

**"The bundle version must be higher…"** — the build-number stamp did not run.
Check `ci_pre_xcodebuild.sh` is executable (`chmod +x`) and that Xcode Cloud
found `ci_scripts/` beside the `.xcodeproj`. A non-executable CI script is
skipped silently.

**A build that installs but does nothing / shows no purchases** — `cap sync`
did not run, so `capacitor.config.json` is missing from the bundle. The
post-clone assertions should catch this; if they were removed, the symptom is a
working-looking app whose plugins are all `UNIMPLEMENTED`.
